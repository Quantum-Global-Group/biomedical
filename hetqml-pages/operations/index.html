⊙ HOW TO READ THIS PAGE
What this view answers — and what to question

Operations is for platform engineers, not researchers. Read it before kicking off a run. If anything here is amber or red, the science pages will inherit fallback labels — interpret accordingly.

01System Health · Quantum Backends · Job Queuelive · degraded · down
PROVIDES
✓Status of every external dependency: IBM quantum backends (with calibration), classical compute, KG cache, public APIs (PubChem, ClinicalTrials.gov, DrugBank), model registry
✓Active quantum job queue with backend, status, ETA, and progress
INTERROGATE
⊙Is any service degraded? If so, the Experiment page's source check will likely mark a source as fallback — interpret downstream metrics accordingly
⊙What’s the queue wait? If it’s > 30 minutes, kick off the run early or switch to classical path
02Job History · Resource Utilization · Costaudit + finance
PROVIDES
✓Last 24h of completed jobs with full provenance: candidate, top model, duration, cost, integrity-guard posture
✓Quantum-seconds and CPU-hours consumed this month against budget; per-service spend breakdown
INTERROGATE
⊙Are any jobs failing repeatedly? Failure clusters indicate a systemic issue, not an individual run problem
⊙Is the budget burn-down ahead of pace? If MTD spend > (today’s day / month days × budget), throttle
03Data Sources · Alertsfreshness · integrity
PROVIDES
✓Last-refresh timestamp + SHA-256 hash for every upstream snapshot (Hetionet, PubChem, ClinicalTrials, DrugBank, DOID)
✓Active alert list and resolved incidents from the last 7 days; MTBF / MTTR if relevant
INTERROGATE
⊙Is any data source older than its SLA? Stale data quietly degrades reasoning quality
⊙Are recent alerts clustered around a single service? If so, that service may be on the edge of failure
